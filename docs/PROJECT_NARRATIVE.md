# 项目叙事重构 —— 从「技术栈堆砌」到「问题 → 方案 → 结果」

> 用途：面试自我介绍 / 项目讲稿 / README 核心段。目标：每个技术点都以「遇到什么问题 → 怎么解决 → 带来什么结果」讲，而不是罗列框架。

---

## 0. 一句话定位

> 一个高并发的**在线抢位预约系统**。核心难点不是「用了多少框架」，而是单行热点库存如何做到 **2000 并发零超卖**、以及订单在 15 分钟超时/场次关闭时如何**自动取消且不重复回滚**。整个项目的取舍都是围绕这两个问题展开的。

---

## 1. 问题：秒杀式抢位，库存打穿

**业务场景**：一个剧本杀场次放了 6 个名额，开抢瞬间可能有几千人同时点。谁成功、谁失败必须严格按先到先得，且**绝不能超卖**。

**初版做法（踩坑）**：直接在 MySQL 上做乐观锁
`UPDATE session_info SET booked=booked+1 WHERE id=? AND status=1 AND booked+1<=capacity`
- 面试时能答出的坑：这是**单行热点数据**，所有抢位请求都在抢同一行（同一个 session id）。
  InnoDB 行锁把并发**强行串行化**，越往后锁等待越久；
- 压测到 2000 并发时：产生约 **24000 次 SQL**、DB CPU 持续飙高、响应恶化。
- 本质：把「秒杀」压到关系库的写行锁上，数据库成了瓶颈。

---

## 2. 解决：让 Redis 挡第一层，DB 只做结果校验

取舍核心：**扣减要原子，且别把竞争压给 MySQL**。

- **Redis+Lua 原子扣减**（方案 A）
  - 库存放 Redis HASH `session:{id}`，录 `booked / capacity`；
  - 一次 Lua 脚本内完成「判断 + 扣减」：`if booked+playerCnt<=capacity then HINCRBY booked playerCnt return 1 else return 0`；
  - **判断和扣减在同一个脚本原子执行**，天然杜绝了"先读后写"的竞态；
  - key 加动态 TTL，防止陈旧库存常驻内存。
- **Redisson 分布式锁防重复提交**：`reserve:lock:{sessionId}:{userId}`，同一个人同一场次只能下一单。
- **DB 兜底 + 降级**：Redis 正常时请求根本不打 MySQL，DB 只负责记最终结果；
  Redis 宕机时（只捕获 Redis 连接/系统异常）自动回退 MySQL 乐观锁，并**异步 forceRefreshBooked**
  把 MySQL 的真实 booked 回刷 Redis，保证 Redis/MySQL 最终一致。

---

## 3. 结果：一个可被面试追问、又有硬数据的结论

用 2000 并发压测（实测，2026-09-04）、能力 10 名额：

| 指标 | MySQL 乐观锁（方案 B） | Redis+Lua（方案 A） |
|---|---|---|
| 冲突率 | **86.5%**（1668/1730 个请求被锁击穿） | **0.000%** |
| QPS | **≈ 20**（97s 才跑完） | **≈ 192**（峰值 669，2.99s 清空） |
| 库存 booked | 10/10（字段未超卖） | 10/10，与成功数完全一致 |
| 订单层 | 出现 22>10 越量 → 需靠唯一约束兜底 | 严格 =capacity |

一句话：**把抢导致命的热点写的冲突，从数据库行锁挪到了 Redis 的 Lua 原子脚本，
实测冲突率 86.5% → 0、QPS 20 → 192，且 Redis+Lua 严格零超卖。**

→ 这一段能承接面试官所有追问点：Lua 为什么原子？为什么不直接 HINCRBY？
   Redis 挂了怎么办？Redis 与 MySQL 不一致怎么修？（答案都在上面的方案里。）

## 4. 第二个问题：订单的「最终一致性」

抢到名额但 15 分钟不付钱，要自动作废并**放回名额**；主办方临时关场，要把**所有未支付订单批量取消并回引流**。
两处都怕：**重复回滚**（把别人的名额扣了）和**误取消已支付单**。

**方案**：RabbitMQ **TTL + 死信队列（DLX）**实现延迟关单
- 下单就发一条延迟消息到 `order.delay.queue`，队列配 `x-dead-letter-exchange / x-dead-letter-routing-key`，
  到期自动流转到 `order.dlx.queue`；
- 消费者是**幂等**的：先查订单 `status=0`（待支付）才取消，否则直接跳过；
- 取消时**同时回滚** Redis 库存与 MySQL `booked`，双重保险；
- 场次关闭 `closeSession()`：开场前 2 小时外允许关闭，关闭后删 Redis `session:{id}` 缓存、状态置 0，
  再由消费者**批量取消待支付订单、回滚库存**。

**结果**：超时自动关单与关场批量取消两条链路都用「状态位 + 幂等 + 双写回滚」保证最终一致，
不会重复回滚、不会取消已支付单。

## 5. 第三个问题：微服务拆了，怎么防越权

5 个服务拆开后只有网关不行——服务内角色校验、服务间 Feign 调用都要防护。

**方案（三段式）**
1. **入口**：Spring Cloud Gateway `JwtAuthFilter` —— 白名单（注册/登录/内部接口）直接放行；
   有 token 校验签名并注入 `X-User-Id / X-User-Role`；
2. **服务内**：`@RequireRole` + `@Around` 切面统一角色鉴权；
3. **服务间**：`InternalApiKeyFilter` 拦 `/**/internal/**` 验 `X-Internal-Api-Key`，
   Feign 用 `InternalApiKeyInterceptor` 自动带该头；密钥放 Nacos `urban-shared-config` 一处管理。

**结果**：公网 → 服务内 → 服务间三层隔离，任一环缺失都无法越权；密钥不再散落各服务。

## 6. 演进与教训（面试加分项，主动说出"我踩过的坑"）

- **坑 1**：初版 MySQL 乐观锁在单行热点下 2000 并发≈24000 SQL、DB CPU 飙升 → 教训：
  **秒杀类的竞争不该让关系库行锁去背**，把原子性交给 Redis Lua、DB 只记结果。
- **坑 2**：降级策略一开始捕获过宽，会把业务错误也吞掉 → 收敛为只捕获 Redis 连接/系统异常，
  并异步校准，保证 Redis/MySQL 一致。
- **坑 3**：RabbitMQ 延迟消息首次用插件失败 → 改用**纯 TTL+DLX** 原生方案，不引入额外插件，
  部署更稳。

> 用「三个问题+三个方案+可量化结果+踩坑教训」讲完，全程不背框架名，面试官会顺着你挖，而你每个点都有代码和压测数据兜底。
